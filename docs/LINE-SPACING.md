# Paragraph line spacing

Home > Line spacing and Paragraph now offer Multiple, At least and Exactly. Multiple uses a line multiplier; the other rules use typographic points. The style editor exposes the same rule. Layout > Single, 1.5 lines and Double reset the rule to Multiple. Applying a rule/value is one undo step, works in table cells and preserves the selection. Cancel leaves the document unchanged.

The shared layout uses the specified exact height for line advance and pagination, and intersects its clipping region with a containing table cell. Short exact lines bottom-align and clip text from the top; excess height centers the text. Minimum spacing grows to accommodate taller runs. List markers follow the text baseline. Screen and PDF use the same geometry. This follows the positioning described by [Microsoft's OOXML line-spacing documentation](https://learn.microsoft.com/en-us/dotnet/api/documentformat.openxml.wordprocessing.spacingbetweenlines.line?view=openxml-3.0.1); it does not establish general Word-rendering equivalence.

Native files and DOCX retain the rule and value, including named styles and tracked paragraph-format history. Before/after spacing overrides preserve inherited line settings. Style updates preserve a direct rule/value override as a pair, so points cannot accidentally become a multiple. Legacy native files without a rule retain their existing multiplier. DOCX stores multiples in 240ths of a line and point values in twips. Values smaller than 0.06 remain unsupported; DOCX input is clamped to that minimum. HTML/text interchange does not retain all spacing behavior.

The reusable atomic command is `paragraph.spacing {"rule":"exact","value":18}`. Rules are `auto`, `atLeast` and `exact`. `paragraph.set` and `styles.modify` also accept the `lineRule` property. Their existing `spacing` property edits the numeric value in the current rule's units.

Acceptance scripts are `line-spacing-probes.py`, `render-line-spacing-probe.py` and `live-line-spacing-smoke.py`. The paired CLI checks assert six rules/values in both apps and reciprocal DOCX round trips. The renderer independently exports the same three-paragraph fixture through both CLIs, rasterizes with Poppler and measures line advance. Fonts and baseline positions are reported separately from matching line advances. Tight 6-point lines touch in the raster, so their individual advances cannot be measured from ink bands; the fixture instead checks clipping to the line area.

Wordcraft remains pinned at `159b84f54c74e9e82fb3109b758ae7dd6f4e3ab0`. Its 24-point exact/minimum line advances match, but baseline positions differ. In the tight fixture, Wordcraft draws above the line area while this app clips to it. Those differences are retained as evidence, not a full rendered-parity pass. Native builds still use the isolated 008f9ece-based framework plus recorded Mac fixes; current-release integration and all-platform acceptance remain outstanding.

The final candidate passes 478 Java 8 tests, 72 native accessibility/UI checks (36 each on Mac and iPhone), 24 paired spacing checks, 24 paired row regressions and 59 paired document cases. The original document XML and recipient state were restored exactly and both task-owned apps stopped; the Mac window and 214% zoom were restored after testing at 100%. Native spacing checks include dialog cancel/apply/reopen, one-step undo/redo, selection preservation, full Paragraph dialog, preset unit reset and actual visible line-height/clipping diagnostics. Named-style behavior is covered by library/interchange tests; this checkpoint does not certify every style-editor native workflow. Exact source/binary hashes and restoration status are recorded in `line-spacing-acceptance.json`. Full parity remains incomplete; see [STATUS.md](STATUS.md).
