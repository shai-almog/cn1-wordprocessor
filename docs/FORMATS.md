# Format boundaries

| Format | Current behavior | Limits |
| --- | --- | --- |
| `.cn1doc` | ZIP with native document XML and optional original DOCX | Primary editable storage for implemented model; not a Word format. Undo history is not serialized. |
| DOCX | Paragraphs, inherited paragraph/character styles plus direct formatting, spacing/alignment/indents/periodic tabs/page geometry, nine-level lists with simple labels/restarts, hyperlink relationships, range comments with replies (ranges in the body, table cells, notes, header/footer stories and text box stories, header and footer table cells included, as Wordcraft's comment marks in any story; a range stays within one text box story), resolved state, initials and rich (formatted) comment bodies, named paragraph style definitions, paragraph-level embedded PNG/JPEG/GIF/BMP/TIFF/WebP/WMF/EMF pictures, named table styles with conditional formatting (w:style w:type="table", w:tblStylePr, w:tblStyle, w:tblLook; re-derived after row/column insert or delete and sort, as Wordcraft keeps the style reference live, though direct cell shading in a styled table is re-derived with it), floating tables (w:tblpPr and w:tblOverlap; laid out as Wordcraft place_floating_table: never split, moved whole with its anchor to the next page when it does not fit, kept below earlier floating tables when overlap is "never", text wrapping both sides), table-property revisions (w:tblPrChange/w:trPrChange/w:tcPrChange), the document default language (w:docDefaults w:lang), rectangular table content with horizontal/vertical merges and rich cell paragraphs | Theme fonts/colors, custom/composite list labels, bookmarks inside field results, floating/cropped/rotated pictures, structural/move revisions, advanced fields/sections and advanced table properties are incomplete. Compatibility warnings accompany unsupported constructs. |
| ODT | Import translates `content.xml`/`styles.xml`/`meta.xml` and `Pictures/` into WordprocessingML and reads it with the DOCX reader; export writes the DOCX package and translates it to ODF 1.3 (stored `mimetype` first, manifest, content, styles, meta, pictures). See [OpenDocument Text](#opendocument-text-odt). | First master page only; comments (annotations), tracked changes, text boxes, fields, paragraph tab stops and multi-section layouts are not carried, all shared with Wordcraft's ODT reader/writer (one master page; it also skips notes, which are kept here). Paragraph borders are read and written (`fo:border`, `fo:border-top/bottom/left/right`), as Wordcraft reads a bottom border as its rule and writes its rule that way. |
| TXT | UTF-8 text, paragraph breaks, table text, picture descriptions | Formatting is discarded by definition. |
| HTML | CN1 text import plus tables (`colspan`/`rowspan`, clamped to 1000x64) and `<img>` PNG/JPEG `data:` URIs plus external `http`/`https`/`file:` and relative-path images (relative to the opened file) fetched through Codename One networking/FileSystemStorage with a 20 MB limit; styled HTML export including merged tables, embedded data-image pictures and superscript/subscript | Cell text uses the CN1 text importer (nested tables flatten to text; table/cell CSS, header rows are not imported). Images that fail to load or aren't PNG/JPEG are left out and listed in a warning when the file is opened; pasted HTML and CLI/macro HTML imports have no source location and skip external images. Fetches block the import (via addToQueueAndWait on the EDT) with a 15 s timeout per image. Not a browser document renderer. Tables nested in cells are written inside their `<td>` and read back as nested tables. |
| Markdown / RTF / AsciiDoc | CN1 rich-text adapters; Markdown GFM pipe tables (column alignment, `<br>` cell breaks) and `![alt](data:)` PNG/JPEG images (external and relative image targets load as for HTML when a file is opened); RTF `\trowd` tables with `\clmgf`/`\clvmgf` merges and tables nested in cells (`\itap`, `\nestcell`, `{\*\nesttableprops ...\nestrow}{\nonesttables}`, any depth) and `\pict` `\pngblip`/`\jpegblip` pictures, both directions | Supported text subset only. Markdown has no merged cells: as in Wordcraft's markdown writer (`table_md`), a column or row span exports as empty covered cells (`| a |  | b |`), and a bare `||` imports as an empty cell (no MultiMarkdown colspans, as in Wordcraft's reader). RTF cell text keeps only bold/italic/underline/strike/alignment; cell widths, borders, shading and differing per-row `\cellx` grids are not imported. Drawings and AsciiDoc tables/pictures are rejected. AsciiDoc output is CLI-accessible. |
| LaTeX (`.tex`) | Export: standalone `article` (fontenc/inputenc/textcomp, plus ulem/xcolor/multirow/longtable only when used, hyperref) with `\title`/`\author` from document properties, unnumbered `\section*`..`\paragraph*` from Heading1-4+, bold/italic/underline/strike/small caps/monospace/super/subscript/color/font size, center/flushright/quote, nested itemize/enumerate (max 4 levels), `tabular`/`longtable` with `\multicolumn`/`\multirow`, `\href`, `\footnote`, bookmarks as `\label` and REF/PAGEREF fields as `\hyperref`/`\pageref`, escaping of TeX specials and Unicode punctuation. Import: tolerant parser for sectioning, `\title`/`\author`/`\maketitle`, text commands and declarations, sizes, colors, accents, ligatures/quotes, lists/description, quote/center/flush environments, verbatim/`\verb`, `tabular` with `&`/`\\`/`\multicolumn`/`\multirow`, `\footnote`, `\url`/`\href`, `\label`/`\ref`/`\pageref`, captions, `\cite` as bracketed keys; unknown macros keep their braced text | Not a TeX engine: user macros are not expanded and `\input` files are not read (the same in Wordcraft). Equations export as math (`\[ \]`, `$ $` for inline, `equation*` with `\tag` when numbered, `amsmath` added): fractions, scripts, radicals, n-ary operators, `\left`/`\right` delimiters, matrices, accents, bars, functions, limits and braces. Import: `$...$`/`\(...\)` become inline equations and `\[...\]`, `$$...$$` and equation environments display equations, parsed by `MathLatex` (Wordcraft's `math_latex` parser: fractions, scripts, radicals, n-ary operators with operands, delimiters, matrices, cases, aligned rows, accents, braces, limits, text); LaTeX spacing is not kept (`E = mc^2` reads as `E=mc^2`, as in Wordcraft), bold/sans/monospace math styles are not modeled and unknown commands stay as text. Pictures export as their alternative text (single-file export, as in Wordcraft); `\includegraphics` imports as a `[Picture: file]` placeholder. Endnotes export as footnotes; bookmarks export as point labels at paragraph start (ranges are lost). Multi-paragraph table cells are joined into one line; column widths, borders and shading are not exported. Non-Latin text needs XeLaTeX/LuaLaTeX. Exported output was not compiled in CI (no TeX installation available). |
| PDF | Paginated text/table/picture export, colors and decorations; embeds the bundled faces, with Hebrew and Arabic falling back to bundled Noto faces; kerning, links, outline, metadata and tags | Shaping covers Latin, Hebrew, Arabic, the nine major Indic scripts, Thai, Lao, Khmer and Myanmar; CFF fonts embed with charstring and subroutine subsetting, CFF2 fonts embed whole; no PDF import. |

Unedited DOCX export uses the original XML/asset part bytes; ZIP bytes/metadata may differ. An edited DOCX with compatibility warnings is blocked until the user exports an explicitly converted copy. Saving `.cn1doc` retains the editable representation and source DOCX for later recovery. Original assets remaining in a converted ZIP are not evidence of unchanged document semantics.

Bounds: DOCX has at most 4,096 entries, 32 MiB expanded per entry and 128 MiB total expanded data. XML has a 32 MiB input limit, depth 256 and a node limit; DTD/entity declarations, malformed nesting and duplicate attributes are rejected. Native XML rejects unknown versions and duplicate block IDs. File adapters cap input at 128 MiB.

There is no claim of arbitrary DOCX losslessness or pagination equivalence. Use the compatibility report and keep the source document when testing imports. Font substitution and incomplete styles can change line and page breaks even before editing.

CLI PDF pagination measures the bundled TrueType advances used by the exported PDF. CLI/MCP page-reference commands use those same metrics; native commands use the editor's print-layout engine, independent of mobile reflow. Native platform font metrics can still differ from headless metrics. PDF glyph positions apply GPOS/`kern` pair kerning inside each span while keeping the layout span origins, so kerned text can end slightly before the measured span edge. Complex shaping equivalence is not claimed. The low-level `PdfExporter.write(document)` overload and default standalone `Commands()` retain the explicit Helvetica fallback; application hosts supply their layout engine/font provider. Fonts and licenses are listed in [third-party notices](../docs/third-party/README.md).

The GUI now bundles Source Sans 3, Source Serif 4 and JetBrains Mono (OFL licenses included). Imported family names outside those families are substituted. Native and CLI PDF export use the bundled fonts. Basic numbered lists restart after non-numbered paragraphs. Simple nested levels, start overrides and Roman/letter formats round-trip; composite numbering text such as `%1.%2` remains an explicit approximation. The hollow-circle and square nested bullet markers are exported as vector geometry in PDF.

Comments use standard range markers and `comments.xml`; resolved state uses paragraph IDs and `commentsExtended.xml`. Rewriting regenerates the extended metadata to match the rewritten comment IDs. Replies use linked comment paragraphs and preserve author, text, date (`w:date`) and resolution; the native format keeps comment and reply `date` attributes, Word 2003 XML `aml:createdate` is imported, and `.doc` comment dates are not read (as in Wordcraft). Editing thread/reply text preserves that metadata; leading, interior and trailing blank paragraphs survive native/DOCX round trips. Body ranges and ranges within one table cell, including multiple cell paragraphs, are supported. Ranges across cells and from body text into a table (in reading order, as Wordcraft's body story) and ranges within a footnote/endnote story are written with markers in `document.xml`/`footnotes.xml`/`endnotes.xml` and read back; header/footer and text-box ranges remain unsupported. Comment anchors follow explicit edit ranges, including repeated text, and undo restores the previous anchors.

Clipboard copy publishes native document XML, HTML and plain text. Native XML preserves implemented paragraph/run/table properties; macOS returns private MIME data as UTF-8 bytes. The paste path decodes those bytes before using the model. External HTML still uses the limited CN1 text importer and does not establish full Word clipboard interoperability.

Superscript/subscript preserve base point size plus baseline alignment in native XML and DOCX; screen/PDF rendering uses a smaller shifted glyph. Mixed font sizes share a line baseline. Merged cells preserve owning paragraphs and serialize DOCX gridSpan/vMerge and HTML row/column spans. Table column proportions, minimum row heights, solid uniform cell borders, shading, symmetric padding, vertical alignment and repeated leading header rows now persist in native/DOCX and render in screen/PDF. Nested tables, asymmetric/decorative borders and floating positioning remain incomplete; DOCX conversion warnings identify these cases. Periodic fallback tabs serialize a bounded sequence of 64 positions; explicit aligned tabs and leaders are supported as described below.

Pictures retain the original PNG/JPEG/GIF/BMP/TIFF/WebP/WMF/EMF bytes in native/DOCX files. WMF (placeable or standard header) and EMF pictures, including `.doc` metafile BLIPs (inflated, with a placeable header restored for WMF), are rasterized in pure Java to a PNG of at most 2048 pixels per edge (144 dpi below that) for display, HTML and PDF, so PDF output is a bitmap rather than vector art. The rasterizer covers the record subset Wordcraft reads: window/viewport/map modes, EMF world transforms, save/restore, pens, solid brushes and stock objects, lines, polylines, polygons, poly-polygons, Beziers, rectangles, ellipses, arcs/chords/pies, EMF path brackets and DIB bitmaps (StretchDIBits, DIB(Stretch)BitBlt, BitBlt/StretchBlt/AlphaBlend). Text records are not drawn and hatch and pattern brushes paint as solid color (both also in Wordcraft, whose PDF output is likewise a bitmap); rounded rectangles are drawn square, and clipping, regions and raster operations other than copy are ignored; unknown or malformed records are skipped and fill work is bounded. GIF (first frame only; animation is dropped), BMP (1/4/8/16/24/32-bit, uncompressed, bitfields, RLE8/RLE4), baseline TIFF (first page; uncompressed, PackBits, LZW, Deflate; bilevel/gray/palette/RGB/RGBA at 1-16 bits, strips or tiles, horizontal predictor) and WebP (lossless VP8L, lossy VP8 key frames, ALPH alpha) are decoded by pure-Java decoders and converted once to PNG for display, HTML and PDF. Animated WebP, planar/CMYK/YCbCr/JPEG-compressed/floating-point TIFF and OS/2 BMP variants beyond the 12-byte core header are rejected with a clear error. Display uses a bounded decoded-image cache and a maximum 2048-pixel preview edge; exports use original bytes. Images are bounded to 20 MiB and 16 megapixels. PNG PDF decoding supports non-interlaced grayscale, RGB, indexed and alpha images (including packed samples and 16-bit samples converted to 8-bit PDF pixels); interlaced PNG PDF export fails explicitly. JPEG PDF export embeds the encoded data without recompression. Floating DOCX placement, crops and rotations produce conversion warnings; picture-in-text import moves the picture after its paragraph and warns. Cell pictures (body, nested and header/footer tables) round-trip through native, DOCX, ODT and HTML; RTF writes them as `\pict` in their cell paragraph and Markdown as `![alt](data:)` images in the cell, as Wordcraft's writers do (drawings in cells are written as an alt-text figure in Markdown and left out of RTF).

Paragraph styles store resolved character and paragraph defaults. Changing a definition updates matching body/cell paragraphs while retaining properties differing from the prior defaults. Inheritance is flattened on edited export; linked character styles, style sets and a full Word style inspector remain incomplete. A direct override equal to its previous default cannot be distinguished from inheritance in the current model.

Native PDF export and print embed the same Source Sans 3, Source Serif 4 and JetBrains Mono faces used by the editor (four variants each), with CID glyph maps, widths and Unicode extraction maps. Each TrueType face is embedded as a subset: glyph ids are kept (identity CIDToGIDMap) but outlines the document does not use are emptied, after closing over composite-glyph components, and layout tables are dropped; the subset carries a format 12 cmap of its kept glyphs and a six-letter subset tag. CFF-outline faces (.otf, CFF .ttc collections) are rewritten as a CID-keyed CFF holding .notdef and the used charstrings in CID order (FontFile3 /CIDFontType0C, no CIDToGIDMap); the kept charstrings are interpreted to find the global and local subroutines they reach, and every other subroutine is replaced by a bare return so the INDEXes keep their biased numbering and no charstring is rewritten. CFF2 (variable CFF) faces are embedded whole as FontFile3 /OpenType with CID = glyph id, so a glyph reused for different text extracts as its first text. A character the chosen face lacks falls back per character to bundled Noto Sans Hebrew and Noto Naskh Arabic (regular/bold), then to installed fonts: the platform font folders (macOS /System/Library/Fonts, /Library/Fonts, ~/Library/Fonts; Windows Fonts folders; /usr/share/fonts, /usr/local/share/fonts, ~/.fonts, ~/.local/share/fonts) are indexed once by family name through FileSystemStorage and candidates are tried in Wordcraft's per-script order (its preferred families for Devanagari, Bengali, Thai, Lao, Khmer, Myanmar and other Indic scripts, its RTL list for Arabic/Hebrew, then families named after the script, then its general fallback list, at most 24 faces per character). Characters nothing covers print as the face's .notdef box. Text is shaped per face and script run by a built-in OpenType engine: GSUB single, multiple, ligature, context and chaining-context lookups (ccmp, locl, rlig, liga, clig, calt; Arabic isol/fina/medi/init by joining type; Indic nukt, akhn, rphf, rkrf, pref, blwf, abvf, half, pstf, vatu, cjct, pres, abvs, blws, psts, haln with pre-base matra reordering, two-part matra splitting (Bengali, Oriya, Tamil, Malayalam) and reph placement for Devanagari, Bengali, Gurmukhi, Gujarati, Oriya, Tamil, Telugu, Kannada and Malayalam; Thai/Lao sara am decomposed with the nikhahit moved before preceding tone marks; Khmer and Myanmar syllables with pre-base vowels, coeng Ro / medial Ra moved before the base, kinzi after it, and rphf, pref, blwf, abvf, pstf, cfar) and GPOS single, pair, mark-to-base, mark-to-ligature, mark-to-mark, cursive attachment and context lookups (kern, curs, mark, mkmk, dist, abvm, blwm), honoring GDEF lookup flags. Marks and offsets are placed with TJ adjustments and text rise. Faces without Arabic GSUB still use Presentation Forms-B and lam-alef. Right-to-left runs are drawn in visual order with mirrored paired brackets. ToUnicode maps give each cluster's logical text on its first glyph (ligatures, reordered Devanagari syllables), so extraction stays in logical order. Hyperlinks become URI link annotations (http, https, mailto, ftp) and bookmark links become page destinations; headings build the PDF outline; title/author/subject/keywords, creation date and the first run language become document metadata. Output is tagged: paragraphs, headings H1-H6, tables (Table/TR/TD) and figures with alt text are structure elements with marked content and a parent tree; headers and footers are artifacts.

PDF limitations: color-bitmap emoji fonts cannot be embedded and are skipped, so a script only those fonts cover still prints as .notdef; shaping implements Latin, Hebrew, Arabic, the nine Indic scripts, Thai, Lao, Khmer, Myanmar and Hangul (jamo composed to precomposed syllables or given ljmo/vjmo/tjmo, as HarfBuzz); USE scripts (Tibetan, Sinhala, Javanese, Balinese, Sundanese, Batak, Cham, Lepcha, Brahmi and the other non-joining USE scripts, when the font has their GSUB script) go through the Universal Shaping Engine ported from harfrust (its Unicode 17 category table and syllable machine, rphf/pref recording, reordering, topographical forms and dotted circles in broken clusters); Mongolian, N'Ko, Phags-pa, Adlam and Hanifi Rohingya take Arabic joining forms inside USE, and its pre-reordering lookups stay within a syllable, as harfrust; Syriac takes the Arabic shaper with fin2/fin3/med2 and Mandaic, Manichaean, Psalter Pahlavi, Sogdian, Old Uyghur and Chorasmian join inside USE, as harfrust; faces with `morx` but no GSUB script for the run (macOS Kailasa, Malayalam MN/Sangam MN, Silom and other Thai system fonts) are shaped with AAT `morx` and positioned with `kerx` formats 0/1/2/4/6 or `kern` plus `trak`, as harfrust (morx chains keep their default settings because Wordcraft requests no feature with a morx mapping, as in Wordcraft); GSUB reverse-chaining lookups, variable-font instances and vertical text are not supported; Indic reph is placed after the base; Telugu forms reph only with an explicit ZWJ (Ra, virama, ZWJ), as HarfBuzz; Malayalam dot reph (U+0D4E) opens the following syllable and moves after its main consonant, as HarfBuzz's logical repha; per-script shaping is checked against installed macOS fonts and synthetic tables, not against Wordcraft output and its below-base forms rather than by the font's full positioning class; Arabic shaping does not join across span boundaries and Arabic layout widths are measured unkerned; bracket pairing follows the layout's bidi runs; italic/bold Hebrew and Arabic use the regular or bold Noto face; the Helvetica fallback path still rejects text outside WinAnsi; tags do not yet cover lists (L/LI), notes as Note elements, link annotations as Link elements, or reading order across floating pictures. CLI export uses the same embedded bundled fonts and glyph advances.


Aligned paragraph tabs preserve explicit positions, left/center/right/decimal alignment and dot/hyphen/underscore/middle-dot leaders through native and DOCX files. PDF renders the leaders while the document retains actual tab characters. Decimal alignment currently uses a period; right-to-left paragraphs measure stops, indents and alignment from the right, in table cells too, with float cuts mirrored, the drop cap hanging at the right edge and the list label right of the text (as Wordcraft's para.rs); bar stops and inherited clear overrides are supported. DOCX paragraph-specific fallback intervals are materialized to a bounded set of stops; HTML/plain-text adapters retain tab text but do not reproduce this page geometry.


Inline fields now round-trip native instruction/result/lock/code-view metadata and DOCX simple fields. Complex begin/separate/end fields import as atomic objects with cached text; nested result fields and mixed result styles are flattened with warnings. Field instructions are data, never executable code. Unsupported instructions keep their cached result. HTML/text export uses displayed results; it does not preserve field identity. Page/title resolution and host date/time/filename values are explicit updates. Multiline/tab field results currently display spaces while retaining their original cached value in native/DOCX storage (shared with Wordcraft, whose atomic `Field` result is likewise shaped as one atomic run, `crates/layout/src/para.rs` `shape_atomic`, not laid out as tab stops or line breaks). Citation managers' `ADDIN` fields (Zotero, Mendeley, EndNote `EN.CITE`/`EN.REFLIST`) are range fields as in Wordcraft's DOCX reader (`is_range_instr`): a start mark, the result as ordinary editable content and an end mark, a bibliography's begin and end markers in different paragraphs included; orphan end marks are dropped on read. Wordcraft also keeps TOC fields as ranges, while here a TOC is generated content; other field types spanning paragraphs are closed at the paragraph end with a warning. Advanced field evaluation is incomplete.


Headers/footers are block stories like Word's and Wordcraft's: paragraphs, tables (nested too) and pictures (inline or floating), with default/first/even variants, distances, different-first/even flags, field objects (resolved per page at any table depth), direct formatting and per-part hyperlink and image relationships. Native XML retains all six variants and writes `table` and `picture` elements in a `story` (version 1 paragraph-only stories still load; unknown story elements are skipped); DOCX reads and writes `w:tbl` and `w:drawing` in header/footer parts. Existing generated parts are reused on edited re-export. Other non-paragraph margin content (`w:sdt`, `w:altChunk`) generates import warnings. Section ownership and links are supported as described below. Layout expands body margins for active variants, bounded to preserve body space; oversized stories may clip. PDF currently resolves page fields in each rendered margin; DOCX keeps field instructions and cached values for external recalculation.


Section update: native storage and DOCX now preserve paragraph section boundaries, paper geometry, next/continuous/odd/even starts, page-number restarts and inherited versus explicitly empty header/footer stories. PDF uses each page's own MediaBox; resolved PAGE results follow section numbering. Oversized margin content produces layout warnings and PDF export fails rather than silently dropping content. `w:gutter` is added to the left margin and written back apart, and `lnNumType` start/distance are honored (as Wordcraft). Columns, mirrored margins, complex continuous-section layout and nondecimal section numbering remain unsupported.

Mirrored margins (`w:settings/w:mirrorMargins`, Layout command `layout.mirrorMargins`) are read, written and kept natively; as Wordcraft's `mirror_even_pages`, even pages put the inside margin and gutter on the right, moving their header, text, notes, footer and column rules to start at the outside margin while page borders stay. Section columns (equal and unequal widths, separator lines) were already supported.


Tracked text insertions/deletions use DOCX `ins`/`del` and `delText`; paragraph marks carry their own revision metadata. Character and paragraph formatting use `rPrChange`/`pPrChange`, with original property values and author/date metadata. Native XML preserves the same history and the track-changes flag. Resolving a selection splits revisions at its boundaries; fields remain atomic. Format-only edits and style changes can be accepted/rejected after native or DOCX reopen. Imported inherited paragraph-style changes also retain their original character defaults. Table property edits are tracked as `tblPrChange`/`trPrChange`/`tcPrChange` with one revision per table, row and cell (Wordcraft's per-element `fmt_change`): each is listed in Review and accepted or rejected on its own (rejecting restores only that element's prior properties), read and written per element in DOCX and native XML, tracked for nested, header/footer and footnote/endnote tables (Wordcraft's fmt_change in any story; nested-table changes resolve inside their cell), and a table with one is marked by the change bar beside its lines.

Supported revision history does not include structural table/image/section edits, style-definition revisions or fully independent overlapping style/run-format histories. The canvas shows All Markup inline and offers Simple Markup, No Markup (final) and Original display (Review > Markup). Tracked moves follow Wordcraft's `cmd/moves.rs`: with Track Changes on, cutting a paragraph or a sentence and pasting it right after records a move (green, double strikethrough at the source, double underline at the destination); accepting or rejecting either end resolves both; DOCX reads `w:moveFrom`/`w:moveTo` (runs and paragraph marks) inside named move ranges and writes them back with their ranges, a move missing an end or whose range never ends staying a plain deletion/insertion; native XML keeps the move name. Table-property revisions follow Wordcraft's `fmt_change` on table/row/cell props: with Track Changes (and formatting tracking) on, a property edit of a body table records a format revision keeping the properties before it; Review lists it as "Table properties", accept keeps and reject restores them; DOCX reads and writes `w:tblPrChange`, `w:trPrChange` and `w:tcPrChange` (written only for rows/cells whose properties differ) and native XML keeps a `previousFormat`. Limitation: one revision covers the whole table (separate row/cell change ids in a DOCX merge into the first found), tables nested in cells or in header/note stories are not tracked on edit, and a cell text direction change is not carried in the prior properties on DOCX read. Balloon layouts are not implemented (Wordcraft: `crates/layout/src/balloons.rs`). Case conversion retains original text when tracking; generic external format adapters do not preserve revision identity. Editing/exporting a DOCX with unsupported content still requires the explicit conversion gate.


Captions use ordinary styled paragraphs containing atomic SEQ fields and optional STYLEREF chapter-number fields. Native XML and DOCX retain instructions/results, including when imported into the other tested implementation and renumbered after an earlier insertion. SEQ supports decimal/Roman/letter output, reset/repeat/hide and heading restarts in body/table order; locked fields retain cached values. Caption placement is a document block operation, not an anchor binding to an image/table. Moving or deleting an object does not automatically move/delete its caption (as in Wordcraft, whose caption is an inserted paragraph, `crates/engine/src/cmd/references.rs`). Margin-story numbering and arbitrary named-style STYLEREF searches remain unsupported (as in Wordcraft, whose `update_seq` in `crates/engine/src/cmd/references.rs` walks only the body and resolves STYLEREF only for heading levels); unknown instructions retain cached results.


## Bookmark and cross-reference ranges (2026-10-14)

The native format and DOCX preserve named ranges in any story (body paragraphs, table cells at any depth, header/footer stories and footnote/endnote stories, as Wordcraft's bookmark marks), including collapsed points, overlapping comment ranges, multiple paragraphs and atomic field boundaries. Bookmarks follow edits, split/join, Unicode case expansion, tracked replacement acceptance/rejection and undo. A range stays within one flow (the body and its cells, one header/footer story or one note story), as comment ranges do. Bookmarks can be added while editing a cell or note, and Go To and REF/PAGEREF cross references reach them (a header/footer bookmark selects nothing in the body, as for comments). Bookmark ranges inside field results remain unsupported; DOCX import reports conversion warnings for them.

Cross-references use live REF/PAGEREF instructions and real named or hidden bookmarks. Heading/caption/bookmark text, logical page numbers and above/below results update explicitly. Nested references resolve without relying on stale cached results; cycles and missing targets produce bounded errors. Locked fields retain their results. Complete Word field-switch semantics and bookmark clipboard transfer are not certified.

Wordcraft imports still report unrelated character/paragraph/section formatting warnings. These checks do not establish complete DOCX fidelity or complete feature parity.


## Generated contents and caption lists (2026-10-15)

Heading-based contents and caption-based figure/table/equation lists are editable paragraph stories with portable TOC, SEQ and PAGEREF fields. They coexist in one document. DOCX export writes standard content controls and complex fields spanning the entry paragraphs, preserving nested page references. Import handles these ranges plus the pinned Wordcraft exports. Native storage retains the same options and bookmarks. Generated labels are refreshed when source headings contain live fields, before pagination settles.

The comparison retains a reference interoperability failure: Wordcraft reads our complex figure-list fields and can edit the source caption, but its Update figures command leaves the generated entries stale. Its updater recognizes atomic TOC fields, not the imported complex field starts. Our app updates Wordcraft's exported lists. This is recorded as three failed reverse-direction checks, not complete round-trip parity. Other unsupported DOCX features still require explicit conversion consent.

TOCs now accept custom style maps, direct outline levels and marked TC entries, including category/level filters. Direct outline levels remain distinct from inherited style levels through native/DOCX storage and tracked-format rejection. Twenty-four paired and two-way import/update checks pass for these sources. Imported level ranges other than 1 through N, per-level page-number suppression, arbitrary complex-field ranges, duplicate lists for the same caption label, custom generated-entry formatting and full Word fidelity remain incomplete. Lists are main-body workflows; figure/caption anchoring to movable objects is not implemented.


## Footnotes and endnotes (2026-10-15)

Native files store an atomic inline reference with an owned rich paragraph story. DOCX uses standard footnotes/endnotes parts, reference elements, automatic/custom marks and part-scoped hyperlink relationships. Notes work in body paragraphs and table cells; their text, formatting and revisions survive round trips. Copying references creates distinct note identities. PDF includes page-bottom footnotes and document-end endnotes; long notes continue over pages. HTML exports linked note sections, and plain-text output retains their text.

Notes default to continuous decimal footnotes and lower-Roman endnotes, with optional custom marks; `w:footnotePr`/`w:endnotePr` number format, start, restart and position are read and written as document defaults and section overrides (`NoteOptions`, `NoteFormats`). A note story holds body blocks as Wordcraft's note parts do: paragraphs, tables (nested too) and pictures, inserted while editing the note (`Session.enterNote`, then Insert Table/Picture), read and written in native files and DOCX `footnotes.xml`/`endnotes.xml` (`w:tbl`, drawings with part-scoped image relationships), resolved by Accept/Reject and laid out in the footnote area (endnotes flow after the body). A footnote's table or picture is placed as a unit (a long note continues on the next page only at a line of its own paragraphs, never through a table or picture, as Wordcraft's NoteBox cuts); clicking a note table's cell on the page enters that cell for editing (Session.enterNoteCell, as Wordcraft's cell_at finds cells in note parts); .doc/RTF/ODT/LaTeX/HTML exports write only the note's paragraphs (as in Wordcraft, whose RTF/ODT/LaTeX/HTML writers write no notes at all and which has no .doc writer); nested notes are not supported; unsupported imported note content is reported or rejected. HTML/text import flattens note semantics. These boundaries do not establish complete Word fidelity.


Note settings now preserve sparse section overrides and document defaults in native XML, DOCX `settings.xml` and section `footnotePr`/`endnotePr` properties. Supported formats are decimal, lower/upper Roman, lower/upper repeated letters, decimal with a leading zero, numeric ordinal, hexadecimal, Chicago symbols, numbers in dashes and no number. Starts are 1–32767; numbering can continue or restart per section, with page restarts for footnotes. Footnotes can sit at the page bottom or below text; endnotes can end each section or the document. Physical printed pages determine page-restarted labels, including when the phone view reflows. Layout reports a warning if page-dependent numbering cannot settle within eight passes.

Roman rendering currently falls back to decimal above 3999; repeated-letter and Chicago labels are capped at 40 glyphs. CJK numbering formats are drawn as Wordcraft's cjk_numbers; Hebrew, Arabic, Hindi, Thai, Russian and Vietnamese are kept and drawn as decimal (as in Wordcraft). Direct in-page editing, custom continuation separators and broader complex-table/continuous-section fidelity remain incomplete. Document labels stored before pagination use document order; the layout and `references.notes` command expose page-resolved labels. Plain-text/HTML exports do not yet resolve page-dependent labels with print pagination.


### Index fields

The document model stores empty-result XE marks and an INDEX marker with generated paragraphs. Native XML and DOCX retain their instruction data, formatted page references, indents and tabs. DOCX export encloses generated entries in a standard multi-paragraph complex INDEX result; import recognizes Index1–Index9, IndexLetter and Wordcraft ListEntry paragraphs. The first body index is managed; additional instances are not certified. Body/table marks, nested subentries, cross-reference text, bookmark ranges and bold/italic page references are supported. Standard page numbering includes section restarts and the space consumed by the index. A missing range bookmark produces an explicit error entry.

Multi-column indexes and unimplemented INDEX switches are rejected during regeneration. Unicode case folding is used for grouping/sorting; locale-specific collation and supplementary-character letter headings are incomplete. XE marks have no visible result; field-code display can expose their instructions, but a dedicated hidden-mark editing UI is absent. Existing DOCX conversion warnings for unrelated source styles/sections still apply. The pinned Wordcraft reader does not preserve the generated INDEX range correctly when updating it.


### Table of authorities

TA citation marks and TOA generated ranges round-trip through native XML and standard DOCX complex fields. TableofAuthorities and reference ListEntry result paragraphs are recognized. Citation text is a single key even when it contains colons. One table, title, leaders and page references are supported; categories, short forms, passim and other TOA switches reject regeneration. Both own exports and imported reference exports pass semantic checks. The pinned Wordcraft reader duplicates our cached TOA range when updating it.


### Citations and bibliography sources

Native XML stores an immutable, document-owned source library and citation style. DOCX uses the standard bibliography Sources custom-XML namespace, Author/Editor NameLists, source metadata and a complex BIBLIOGRAPHY result range. CITATION fields retain tag, page range, cached result and lock state. The source library survives editing, recovery and undo; unrelated package custom-XML stores survive export. Source records are bounded (2,000 sources, 2,000 characters per value, 64-character tags), and duplicate source tags are rejected on import.

Twelve style renderers match paired book/article output fixtures. Author/date bibliography entries have a hanging indent. Composite citations and unimplemented switches retain cached results; filtered bibliographies and unknown styles cannot be regenerated. Corporate author distinctions, broader source roles, note/header citations, locale collation, global libraries and full CSL/style-guide behavior remain incomplete. The pinned Wordcraft reader duplicates our standard multi-paragraph bibliography result on update. Source metadata alone does not establish Microsoft Word rendered fidelity.


Zotero citations use the Word plugin's layout: fields whose instruction is `ADDIN ZOTERO_ITEM CSL_CITATION {...}` or `ADDIN ZOTERO_BIBL {...} CSL_BIBLIOGRAPHY` (instructions up to 1,000,000 characters, other fields stay at 8,192). DOCX writes them as complex fields and reads them back with instruction, cached result and lock. Zotero document preferences are kept as the `zotero.prefs` document setting and written as `docProps/custom.xml` string properties `ZOTERO_PREF_1..n` in 255-character chunks; other custom properties in that part survive. Field results keep their formatted runs (bold, italic, underline, small caps, superscript/subscript) as Word and Wordcraft keep runs between the separate and end marks; they are written back as formatted runs. A Zotero field spanning paragraphs (a bibliography) is read back whole. In the editor a Zotero field is a range (start mark, ordinary formatted text, end mark, as Wordcraft keeps it), so a bibliography is one paragraph per entry; DOCX export writes begin/instrText/separate before the text and end after it. Export repairs orphan marks first (an end with no start is dropped; a start with no end is closed at the end of its paragraph), so output always has balanced begin/separate/end. The native format stores the marks as fields (`formats="range"` on the start, instruction `FIELD_END` for the end); older native files with atomic Zotero fields are converted to ranges when opened. ODT round trip of Zotero fields and preferences is untested. Citations in table cells, footnotes and endnotes are fields in those paragraphs like body ones; their DOCX round trip is not covered by tests, and orphan-mark repair covers body paragraphs only.

Mail merge fields (`MERGEFIELD`, `ADDRESSBLOCK`, `GREETINGLINE`, supported conditional/record rules) retain instruction/cache/lock metadata in native and DOCX templates. Preview updates cached results; Finish converts supported unlocked merge fields to rich text, cloning table/section/note content and remapping comment/bookmark ranges and internal references. Recipient source lists, filtered/sorted views, exclusions and address mappings are session state, not serialized document or recovery data. Completed merges export only the selected records in their selected order. Envelope and label output uses ordinary sections/tables. CSV/XLSX/XLSM/ODS input is a bounded recipient-data import, not a spreadsheet editor.


Document comparison emits normal tracked run and paragraph-break revisions; generated comparisons survive native/DOCX storage and accept/reject in either implementation for the tested subset. Comparison supports paragraph text and text within unchanged table geometry, with direct-format revisions on unchanged paragraphs. It rejects unsupported structures before replacing the current document. Combine and full structured comparison remain incomplete.

## Tab fidelity (2026-10-16)

Bar tabs are stored in native files and DOCX and rendered as vertical rules in the shared screen/PDF layout, including empty and wrapped paragraphs, table cells and margin stories. ## Contextual table layout (2026-10-16)

Insertion above/below/left/right, table-wide equal column weights and minimum row heights, and the nine horizontal/vertical alignment choices are available through the Table Layout ribbon, CLI, macros and live MCP. Horizontal alignment affects every paragraph in the target cells; vertical alignment retains shading, borders and padding. Text selections or rectangular cell selections survive alignment and undo. Insertion below a merged cell uses its far edge; selected row insertion inserts the selected row count. New rows inherit the focused row's cell appearance and minimum height.

Sixty paired editing/DOCX checks preserve cell text, alignment, vertical alignment, shading, row heights and grid proportions across both readers for the tested unmerged fixtures. Row distribution equalizes minimum heights, with a floor of 18 points; content may make individual rows taller. It is not an exact-row-height implementation. Turned cell text (`w:textDirection` btLr/tbRl) is laid out as Wordcraft's turned cells: lines run along the cell's height (the exact row height, else the unwrapped length up to 648pt, the row growing to fit and the text laid out again at the final height), stack across the cell from the right (tbRl) or left (btLr) with vertical alignment moving them across, keep the row on one page, and are drawn, hit-tested and exported to PDF turned. Nested cells take their own direction too: a nested table's horizontal text turns with a turned cell, and a nested cell with its own direction keeps it (inside a horizontal or a turned cell, its frame placed in the outer cell's), as Wordcraft's turned text inside turned text. Pictures inside a turned cell are not turned (Wordcraft turns them), and a nested turned cell does not keep its outer row on one page. Nested tables, asymmetric borders and full merged-table insertion fidelity remain incomplete. Cell/table splitting and AutoFit are described below.

## Drawn objects (2026-10-17)

Shapes, text boxes, WordArt, charts, SmartArt, display equations, ink/canvases, icons, signature lines and object placeholders are block-level `Drawing`s carried by pictures.

- Native XML stores the drawing encoding exactly; a text box's story is a `textStory` element inside its `picture` (paragraphs, tables and pictures as in the body). Files whose text box text is the single `text` property still read and show it as paragraphs; such a box becomes a story when its text is edited.
- Text boxes and shapes hold a block story as Wordcraft's text box parts (2026-10-21): DOCX `w:txbxContent` is read and written as full paragraphs with their runs, paragraph formatting, tables, pictures, bookmarks and comment ranges, in the body, notes and header/footer parts; `.doc` text box stories (`PlcftxbxTxt`) arrive through the same reader (`.doc` is not written, as in Wordcraft). Word 2003 XML VML `v:textbox` content is read as a story (paragraphs with their runs) through its DrawingML conversion. Linked chains (Create Link, the drawing's `linkNext`, kept in the exact drawing encoding of DOCX and native files) flow the first box's story through the chain as Wordcraft does; files whose linked boxes each kept a string show the boxes' texts as one story. Limits: comments are not anchored in group member stories.
- DOCX writes shapes and text boxes as Word shapes (`wps:wsp`, preset geometry, `txbx`). Equation numbers are kept inside the math zone.
- Importing foreign Word shapes and text boxes reads geometry, fill, outline, text and anchoring. Foreign groups produce conversion warnings.
- Charts (2026-10-20): `c:chartSpace` parts are read from their cached values into an editable chart (column, bar, line, pie, doughnut, area, scatter; 3-D, stock, radar, surface, bubble and of-pie map to the nearest type with a warning). Read: series names, categories (or scatter x values), values, stacked and percentStacked grouping of bar/column/line/area charts (drawn stacked or as 100% shares, written back with `c:overlap` 100 on bars), title, legend on/off and value data labels; capped at 29 series and 199 rows. Not read: axis scaling and number formats, colors and styles, secondary chart groups of combination charts (warned), trendlines and error bars. The chart is drawn by `DrawingOps`, so the editor and PDF match. An unedited chart is saved by referencing its original chart part (and embedded workbook) unchanged; an edited or inserted chart is written as a new `word/charts/cn1chartN.xml` with literal data (`c:strLit`/`c:numLit`) and no embedded workbook, so Word shows it but "Edit Data in Excel" has no sheet. Insert > Chart and Insert > Edit Chart Data (CSV) edit charts.
- SmartArt (2026-10-20): the diagram data model is read into the SmartArt text outline (nodes and levels from `parOf` connections) and the layout id is mapped to list, process, cycle, hierarchy, pyramid, radial, matrix or venn. While unedited, it is drawn from the `dsp:drawing` Word saves beside the diagram (preset geometry, solid/scheme fills and outlines, text; gradients, effects, rotation and theme tints are not drawn) and saved by referencing the original diagram parts. Without a saved drawing, or after its text/layout/colors are edited, it uses this app's basic layout; created or edited SmartArt is saved as new diagram parts as Wordcraft writes them (`word/diagrams/datacn1N.xml`, layout, quickStyle, colors and a cached `dsp:drawing` of the node shapes, all relationships of the story part, with content-type overrides). Limits: alignment points, spacing and break properties, other box options and `m:oMathParaPr` are kept only through the verbatim copy, not modeled. Inline `m:oMath` in a paragraph is an inline equation (one object character on the line) written back as `m:oMath` from its linear text, so its OMML formatting is regenerated rather than copied verbatim; display `m:oMathPara` stays a block. Linear input covers a UnicodeMath subset (`a/b`, `x_1^2`, `sqrt(x)`/`√`, `\sum_(i=1)^n`, `(a&b@c&d)` matrices, `\alpha`-style control words, function names, skewed/linear fractions, floor/ceiling/double-square brackets, `〖〗` grouping, combining accents U+20D0-U+20EF and the circled/big n-ary operators). - HTML exports inline SVG.

- Repeating-section items are stored as "; "-separated content.
- Picture controls hold no image.

Character shading, border, proofing language, phonetic guide (ruby) and enclosure (circle/square/triangle/diamond) are stored in `CharacterFormat` and round-trip through native XML. ## Drop caps, picture effects and proofing data (2026-10-17)
- Drop caps are a paragraph property (`dropCap="mode,lines,distance,font"` in native XML). DOCX writes Word's form: a framed `w:framePr w:dropCap` paragraph holding the enlarged letter, followed by the rest of the paragraph. On read, a framed letter paragraph (up to 4 characters) merges back into the paragraph after it. Frame anchoring other than text-relative is not read.
- Picture artistic effects and background removal are stored non-destructively in the native `adjust` attribute (`brightness,contrast,transparency,mode,effect,tolerance`). DOCX does not write them (no `a14:imgEffect` / background-removal mapping), so they are lost when exported to .docx.
- Picture compression rewrites the stored image bytes via the platform image codec (PNG stays PNG; others become JPEG at 0.85).
- Spelling and hyphenation use bundled public-domain Moby word data and CC0 Liang patterns (see `docs/third-party/README.md`).
- Encrypted .docx: agile encryption written as a CFB v3 container (DataSpaces, EncryptionInfo 4.4, EncryptedPackage); read supports CFB v3/v4 and SHA-512 agile only. Hashing, HMAC and AES-CBC come from `com.codename1.security`; encryption and decryption interoperate with `msoffcrypto-tool` on Mac, iOS simulator and Android emulator; the web build is unchecked. Insert Text from File accepts a password for encrypted DOCX.

## Native XML round-trip hardening (2026-10-17)

Native certification loads every recorded before-state through native XML, so the round-trip must be exact:
- Header and footer stories now each get their own id set. Previously a header paragraph could reuse a body id and fail the duplicate-id check on reload.
- Drawing attributes map C0 control characters to U+E000 and up on write and back on read. Raw control characters are illegal in XML 1.0.
- `word_load` loads a document without undo history; history is never serialized (see `.cn1doc` above).

footnotes/endnotes, complex fields, inline PNG/JPEG pictures, comments (PlcfandRef/PlcfandTxt with
GrpXstAtnOwners authors, initials and SttbfAtnBkmk ranges), bookmarks (SttbfBkmk/PlcfBkf/PlcfBkl), tracked
insertions and deletions (sprmCFRMarkIns/Del with SttbfRMark authors and DTTM dates) and main-text floating
objects (PlcSpaMom FSPA anchors joined with the OfficeArt drawing: BLIP-store pictures, embedded or at the
FBSE foDelay offset, preset shapes with solid fill/line colours, and text boxes with their PlcftxbxTxt text;
page/margin/column/paragraph offsets and none/square/top-and-bottom/behind/tight/through wrapping), the same
for header stories (PlcSpaHdr anchors with the header drawing), and OfficeArt groups (SpgrContainer with its
FSPGR space and members' ChildAnchor rectangles, nested groups) written as `wpg:wgp`. The editor model then
treats floating DOCX drawings as it does for .docx (a separate paragraph keeping its wrap kind). Shape line
widths (OPT lineWidth, clamped to 100 pt as Wordcraft does), per-cell shading (sprmTDefTableShd80/
sprmTDefTableShd/sprmTSetShd, as Wordcraft's table decode), per-cell TC80 borders (top/left/bottom/right
Brc80 width, type and colour), paragraph-mark revisions (sprmCFRMarkIns/Del on the mark's CHPX, as an
inserted/deleted paragraph mark), bookmark and comment boundaries on a row-end mark (closed in the row's

imported. Not yet: encrypted or Word 6/95 files (rejected). As in Wordcraft: freeforms (no path read),
gradient fills (the fill colour is used) and formatting revisions are not imported. Wordcraft drops
comments and revision marks.

## OpenDocument Text (.odt)

`Odt.read` and `Odt.write` share the DOCX model mapping: import builds an in-memory DOCX
from the ODF parts, export translates the DOCX writer's package, so `read(write(doc))`
round-trips what both directions cover (tested in `OdtTest`).

Covered: paragraphs and `text:h` headings (outline level mapped to `Heading1..9`), common
paragraph/text styles with parent inheritance and the default style, automatic `P`/`T`
styles (bold, italic, underline, single/double strike, size, font, color, background,
super/subscript, caps, small caps, hidden, letter spacing; alignment, indents, spacing,
line spacing, keep-with-next/together, widows, page break before/after, shading,
right-to-left), `text:s`, tabs, line breaks, hyperlinks (external and `#bookmark`),
bookmarks, footnotes and endnotes, `text:list` bullets/numbering with nine levels, prefix,
suffix, start value and continued numbering, tables with column widths, column/row spans
and cell background, `draw:frame`/`draw:image` with size and `svg:desc`/`svg:title` alt
text, page size, orientation and margins, default header and footer of the first master
page, and title/subject/author/description/keywords.

Not carried: `office:annotation` comments and `text:tracked-changes` (dropped on import,
as Wordcraft does; deleted text stays deleted), text boxes and drawn shapes, fields (their
current text is kept), tab stops, paragraph and table borders (export writes a thin cell
border), first/even-page headers, more than one page style or section, list item
`start-value` overrides and `text:list-header` indentation, table header-row repetition,
embedded objects and formulas. LibreOffice acceptance has not been checked locally
(`soffice` is not installed on the development machine).

## Word XML import: Flat OPC and Word 2003 XML (2026-10-20)

`Docx.read` recognizes a single-file XML document by its first bytes and rewrites it as package
parts for the DOCX reader (`WordXml`); the app opens `.xml` files this way and saves them as a
new file. Import only.

- Flat OPC (`pkg:package`, Word's "Word XML Document"): every `pkg:part` becomes a part, from its
  `pkg:xmlData` element or base64 `pkg:binaryData`, so everything the DOCX reader supports is read.
  Part names are checked for traversal and duplicates; at most 10000 parts and 512 MB decoded.
- Word 2003 XML (`w:wordDocument`): body and styles are carried over, with hyphenated 2003 names
  (`b-cs`, `sz-cs`) and `vmerge`/`hmerge` mapped to ECMA-376 names, `wx:` section wrappers and
  smart tags unwrapped, `aml:annotation` bookmarks converted, and tracked insertions/deletions
  accepted with a warning. Converted into the parts the DOCX reader understands: `w:listDef`/
  `w:list` to a numbering part (`w:nfc` codes mapped to `w:numFmt`, `w:listPr`/`w:ilfo` to
  `w:numPr`/`w:numId`); `w:hlink w:dest` to an external hyperlink relationship (bookmark-only
  links stay anchors); `w:binData` + `v:imagedata` to media parts and inline DrawingML pictures
  sized from the VML `style` width/height (pt/in/cm/mm/px; default 100x50 pt, capped at 20000 pt);
  `v:textbox` to an inline DrawingML text box; `w:hdr`/`w:ftr` in `w:sectPr` to header/footer
  parts (`odd` = default, `first`, `even`); inline `w:footnote`/`w:endnote` to notes parts with
  references; `aml:annotation` `Word.Comment.Start/End/Comment` to comment ranges, references and
  a comments part. `position:absolute` VML shapes become `wp:anchor` floats (left/margin-left,
  top/margin-top, `mso-position-horizontal/vertical-relative` and alignment, `w10:wrap`, negative
  `z-index` behind), and `v:line` (from/to), `v:rect`, `v:roundrect` and `v:oval` preset shapes with
  fill/stroke colors and stroke weight, as Wordcraft's read_vml. VML `rotation` (degrees or `fd`) and `flip`
  are kept as Wordcraft's vml_spin. `Word.Insertion`/`Word.Deletion` annotations are kept as tracked
  changes with their `aml:author` and `aml:createdate`, and comment `aml:createdate` is written to the
  comments part, as Wordcraft's wordml2003 annotation. Limitations: other VML shapes (Wordcraft's
  read_vml reads only line/rect/roundrect/oval), linked (non-`binData`) pictures (Wordcraft maps only
  `binData` names to media) and undecodable picture data are dropped with a warning (as in Wordcraft).
  The comment model has no date field, so a comment's date is not shown or saved back (Wordcraft keeps
  `Comment.date`; this applies to .docx comments too). Namespace prefixes are matched by the
  conventional `w:`/`wx:`/`aml:` names, not by resolved URIs.

Turned table cells (`w:textDirection` btLr/tbRl) turn everything they hold as Wordcraft's `TurnedCell`: text lines, pictures (kept at their size, centred on their turned place and drawn turned a quarter) and nested tables' lines and cell boxes. Nested tables' own cells inside a cell do not turn independently yet (their text direction is ignored).

Markup balloons follow Wordcraft's `balloons.rs`: each unresolved body comment thread (replies under a hairline, author names in Wordcraft's revision colours) is a card in a 216pt markup area right of the page, joined to its anchor by a leader, placed near the anchor, pushed up from the page foot and clipped or left out when a page has too many. The balloon mode (Wordcraft's BalloonMode: `revisions`, `inline`, `commentsAndFormatting`; File > Options > Balloons, `review.balloons`) chooses what the editor shows: formatting changes get "Formatted" balloons, and in `revisions` mode tracked deletions get "Deleted: ..." balloons. In `revisions` mode the deleted text leaves the editor's inline layout (Wordcraft's deletions_in_balloons; it still prints inline). Card text keeps each comment's own run formatting (font, size, bold, italic, colour, underline) and paragraph alignment, wrapped greedily by word (Wordcraft lays the comment part out with its full paragraph engine). PDF export with Print Markup prints the comment balloons with the page scaled down to its paper, and link rectangles are scaled with it, as Wordcraft's PDF writer. Limitations: deletions in headers, footers and notes also leave the layout in `revisions` mode (Wordcraft hides body deletions only); headers, footers, notes and text boxes get no balloons (as Wordcraft).
